# Adding a new service

So far, the number of services available to be deployed with NAPS is quite limited (actually restricted to the services my colleagues and I are using in our respective lab). However, NAPS is designed as extensible framework allowing people to easily declare new services in order to automatize their deployement. 

In addition to the usual nixos-configuration of the service, NAPS provides an interface in order to specify what is needed by a service. As an example, consider the following declaration of the nextcloud service which we will dismantle step by step in this chapter.

```nix

let
    topology= config.naps.topology;
    hostname = "nextcloud.${topology.domain}";
    owner = "nextcloud";
    reload = ["phpfpm-nextcloud.service" "nextcloud-setup.service"];
in {

naps.services.nextcloud = {

    # path to the nixos-configuration of the service
    path = ./default.nix; 

    users.nextcloud = {service="nextcloud"; uid=10003;};
    assets."password" = {
            "nextcloud-admin.key" = {
                generateArgs = {opensslType = "base64"; opensslSize=64;};
                installArgs = {inherit owner;};
                reload = ["phpfpm-nextcloud.service"];
            };
    };
    links = {
        postgres = [
            {database = "nextcloud"; inherit owner reload;}
        ];
        s3 = [
            {bucket = "nextcloud"; inherit owner reload;}
        ];
    };
    persistent = {
        "/var/lib/nextcloud/config" = {shareable=true; inherit owner reload;};
        "/var/lib/nextcloud/data" = {shareable=true; inherit owner reload;};
    };
    endpoints.https = [{
                   hostname = hostname;
                   port = 80; 
                   extraArgs = {tls = "termination";};
                 }];

    configureListen = addr: {
        services.nginx.virtualHosts.${hostname}.listen = [ {inherit addr; port=80;}];
    };

};

```

# Basic options

- `naps.services.<name>.path`:

Specifies the location of the nix configuration file of the service, which will serve as a *default* configuration file. 

```nix
path = ./default.nix; 
```

- `naps.services.<name>.users`:

An attrset describing the users requested by the service. Note that the `uid` should be unique across all the services configured for NAPS.

```nix
users.nextcloud = {service="nextcloud"; uid=10003;};
```

# Assets

Assets are artifacts that are generated by NAPS and provided to each service instance, e.g. passwords, ssh-keys, TLS certificates. Their main characteristic is that they are re-generable and therefore they are not considered to be persistent: for instance, a database password can always be regenerated, and then deployed on both the client and the server without any loss of data, while an encryption key cannot (since a newly generated key will not be able to decrypt the storage).

Asset mechanism provides a robust way against potential attacks or failure. First, assets do not need to be stored in an other place than the machines where they are used. Second, if an asset is suspected to be compromised, it can be regenerated instantly without any effort. Therefore, we highly recommend to use assets instead of persistent datas as much as possible.

Assets are grouped by `providers` which can be seen as their generation backend. For instance, below, you can see that nextcloud requests the asset `nextcloud-admin.key` to be generated by the `password` provider.

```nix
assets."password" = {
        "nextcloud-admin.key" = {
            generateArgs = {opensslType = "base64"; opensslSize=64;};
            installArgs = {inherit owner;};
            reload = ["phpfpm-nextcloud.service"];
        };
};

```

Each provider expects the assets to have two field: `generateArgs` and `installArgs` which serves as parameters of the generation and installation procedure respectively. For instance, the `password` provider uses under the box `openssl rand` and thus requests the parameters to the command. In addition, the field `reload` describes which services should be restarted if the asset changes.
The list of available providers as well as the type of the expected inputs of their respective generation and installation procedure, please consult `naps.lib.assets`.

Obviously, multiple assets coming from multiple providers can be declared, as depicted below (a snippet of the hydra service declaration):

```nix
assets = {
    "password" = {
        "hydra-admin-pass.key" = {
            generateArgs = {opensslType = "base64"; opensslSize = 64;};
            installArgs = {owner = "hydra";};
            inherit reload;
        };
    };
    "ssh-keygen" = {
        "hydra-ssh" = {
            generateArgs = {keyname = "hydra";};
            installArgs = {owner = "hydra"; path = "/var/lib/hydra/.ssh";};
            inherit reload;
        };
    };
    "nix-store" = {
        "hydra-cache" = {
            generateArgs = {keyname = "hydra";};
            installArgs = {owner = "hydra"; mode="0440";};
            inherit reload;
        };
    };
};
```
